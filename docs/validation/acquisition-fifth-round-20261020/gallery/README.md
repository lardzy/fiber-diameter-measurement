# 第五轮：测量证据相册验证

2026-10-20，macOS 本地 Qt 组件检查，应用版本仍为 0.4.10。本目录只说明相册专项结果，不替代主工作台导航、Windows 安装版或真实 Microview 验收。

## 已实现行为

- 当前试验的已接受实测按时间倒序显示，默认全部操作者、全部方向；补计和未存图测量不生成相册卡片。同一文件关联多条测量时，每条记录仍有自己的卡片与几何。
- 提供操作者、方向、类别和证据状态过滤。状态包括“读取异常（已检查）”，明确只筛选已经按需检查的图片，不为筛选扫描或解码整个项目。
- 双击或按 Enter 调用原有单图历史复核，不替换正在查看的历史证据；新测量不抢历史滚动，使用“新增 N 项 · 回到最新”。
- 相册是主窗口所属的非模态可最大化窗口，记忆尺寸、位置、缩略图大小与标注开关。切换试验重置筛选、取消旧代次请求；关闭最终释放控制器。
- 没有证据时明确提示：设置只影响之后接受的测量，未保存的图片无法补回。

## 资源与数据边界

相册仅从当前试验账本和每条测量的证据元数据取图，不扫描文件夹、不读取当前相机画面、不重编码或修改证据文件。缩略图上的测量线由绘制层叠加，关闭相册、筛选、窗口布局与缩略图设置不产生项目业务修改。

模型采用列表视图和绘制委托，不为 10,000 条记录逐条创建图片控件。只请求当前可见范围及相邻一屏，最多 128 个待请求，单个后台文件任务。图片缓存与当前解码预留合计上限 64 MiB；预留覆盖源图、派生缩略图和解码工作空间，包含 16 位 PNG。该数值是相册图片预算，不是整个应用的 RSS 限额。超过预算的源图不在相册后台强行解码，显示“图像较大，双击打开单图复核”；用户主动打开的既有单图复核独立管理其资源。

写入中、写入失败、缺失、损坏及尺寸与元数据不一致均有占位。另存为重定址即使不改变业务 revision，当前路径和读取异常筛选也会失效更新。恢复缺失图片后重新打开相册可重试。

## 自动化结果

运行命令：

```sh
QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest -q \
  tests/test_measurement_evidence_gallery.py \
  tests/test_measurement_evidence_view.py \
  tests/test_trial_records.py
```

重绘优化完成时结果：**58 passed in 4.66s**，其中相册 26 项，已有单图复核及记录模型 32 项。此前 49 项结果之后，增加了“另存为无 revision 更新时清除旧路径的读取异常”回归，并补充关闭控制器的清理。随后增加真实列表项目的单击、双击输入序列回归：单击只选中，完整双击序列恰好打开一次历史复核；这一项未修改产品代码。Windows 随后暴露同毫秒时间戳按 UUID 排序的问题，现仅在相册中使用试验账本持久插入顺序消除时间相同的歧义；每次绑定或业务 revision 变化构建一次序号缓存，比较器不遍历账本，不改共享记录时间列表语义。新增测试固定相同时间戳、反序 UUID、跨视场编号重置及保存重开，并验证排序比较为常量查表。

后续移除了两处重复刷新：图像头读取成功、仅开始解码时不刷新未变化的占位；模型同步后依靠行与结构变化通知，不再额外刷新整个视口。缩略图或错误就绪后，按记录 ID 查找当前筛选中的卡片，只刷新其可见矩形；邻屏预读不刷可见区。新增 5 项实际 Qt 绘制回归验证同图多记录的局部更新、无变化头部阶段、离屏完成、pending→saved/failed 及读取异常筛选的插入、移除和排序。预算、解码质量和业务通知均未改变；该优化减少相册重绘争用，不单独宣称解决所有采集闪烁。

专项覆盖：10,000 条记录仍仅按需解码、128 请求上限、缓存淘汰、解码预留及 16 位 PNG、跨试验旧任务丢弃、保存重定址、缺图恢复、历史滚动锚点、同图多记录、全部操作者和方向、补计排除、pending→saved、撤销重做、只读显示不标脏、窗口关闭与重新打开。

## 原生窗口边界补充

Windows 安装版的 `GetWindowRect` 确认：客户区虽然位于 `[8, 8]`，完整外框仍从 `[-5, -50]` 开始，标题栏确实越界。原来仅检查 `dialog.geometry()`，遗漏了系统边框；这个问题与相册图像内容无关。

现在沿用版本 1 JSON 的客户区坐标，使用实际 [`QWindow.frameMargins()`](https://doc.qt.io/qt-6/qwindow.html#frameMargins) 把完整外框限制在屏幕可用区内，并按四边装饰的实际尺寸压缩过大的客户区。Windows 源验证进一步发现 Qt 可能遗漏透明的缩放边界，因此在 Windows 使用只读 `GetWindowRect`、`GetClientRect`、`ClientToScreen` 计算真实原生外框与客户区的四边差，再按当前 Qt DPR 换算并向上取整，与 Qt 边框逐边取较大值；没有硬编码原生像素，也不修改进程或线程 DPI awareness。原生查询失败时保留 Qt 边框，后续显示复核重试。打开前先创建未显示的原生窗口，取得已可用的边框；显示后再复核一次。恢复普通窗口、返回试验和屏幕移除均复核。最大化、全屏交由系统管理；日常拖动和调整尺寸不持续吸附，不改变业务 revision。

Windows 源验证随后确认外框限位通过，但还原普通窗口时，Qt 的状态已改变而客户区尺寸仍可能暂时是最大化尺寸。现在从旧状态识别该过渡，保留原普通窗口目标，不让中间的移动和尺寸事件覆盖它；复核时采用该目标和最新原生边框，避免把最大化尺寸固化为普通窗口尺寸。

v3 阶段新增 30 项测试覆盖不同边框、负坐标屏幕、过大窗口、旧客户区偏好、真实 Qt `frameGeometry()`、返回及屏幕移除、最大化和全屏返回的精确尺寸、不抢用户拖动、状态先改变而客户区仍为最大化值的事件顺序，以及原生边框在 DPR 1／1.25／2 时向外取整、查询失败保留 Qt 边框并重试。上述同一命令的本地结果为 **88 passed in 5.36s**（相册 56 项、已有复核及记录模型 32 项）；Windows 源码相邻 88 项测试也通过。该阶段通过 **Qt `showMaximized()`／`showNormal()` 方法**触发状态变化，再读取原生坐标：DPR 1 的首显及还原外框均为 `[8, 8, 1066, 791]`，DPR 1.25 均为 `[11, 11, 1326, 971]`；客户区精确恢复为 1040×720 逻辑像素，旧越界位置恢复和重复返回也通过。这些结果没有覆盖系统 UIA／WM 触发状态变化的事件顺序。

随后候选包 **e7310fc5** 的安装版系统 UIA `WindowPattern` 验证发现：首显完整外框正确，但最大化后还原变为 `[8, 8, 2566, 1532]`，未恢复原窗口尺寸。这项失败和原包继续保留在 [安装版失败记录](../windows/frozen-gui/20261020-075048Z-f59413cc/summary.json)，没有放宽尺寸断言。该实际 WM 路径需要继续修复并独立验收；不能把上述 Qt 方法调用路径的通过结果用于证明它通过。最终安装版结果单列于 [Windows 报告](../windows/README.md)。

独立 PowerShell 调用真实 UIA `WindowPattern` 的 [源码事件追踪](../windows/gallery-native-source-uia-failure.json) 随后复现了进入最大化时的另一种顺序：首先到达 Resize、Move，此时 Qt 仍报告普通窗口，连 `normalGeometry()` 也暂时是最大化尺寸，但原生 `IsZoomed` 已为真；之后到达 WindowStateChange，Qt 的 `normalGeometry()` 才恢复正确值。原实现已在前两个事件中覆盖普通窗口偏好，导致稍后的还原目标也错误。

对应修复在移动、调整尺寸和窗口状态事件中只读查询 `IsZoomed`／`IsIconic`，不将受系统管理的过渡尺寸存入普通窗口偏好；可靠的 Qt 状态变化到达后，用其有效 `normalGeometry()` 作为原生查询失败时的恢复依据。查询不会加入相册绘制或缩略图解码路径，不修改原生状态、DPI awareness 或项目数据，也不增加延时常数和反复定位。新增实际 Resize／Move 早于 Qt 状态变化的最大化、最小化两轮回归，以及原生查询失败的恢复回归；同一命令得到 **91 passed in 5.54s**（相册 59 项，既有复核与记录模型 32 项）。

修复后由独立 PowerShell 进程调用真实 UIA `WindowPattern`，让 Qt 主循环自行处理系统状态事件；源码版 DPR 1 与 DPR 1.25 各连续两次最大化／还原均通过，客户区精确恢复 1040×720，普通态原生外框分别恢复 `[8, 8, 1066, 791]` 与 `[11, 11, 1326, 971]`。事件记录确认过渡期间的普通窗口偏好没有被覆盖，见 [DPR 1 完整源码追踪](../windows/gallery-native-source-uia-final.json)。最大化外框由 Windows 管理，不套普通态完整包含断言；还原尺寸和普通态边界断言保持严格。修复后的实际安装版仍单独验收，不以源码通过代替。

该修复源 SHA-256 为 `6bc1ad4ce17a18a8fb729ccaf7bae5f6491d5bc0b67e315f3a7a669275f36ae8`，相册测试 SHA-256 为 `bad9f2c589d854f1972b8fdd8506523e0625fe498b3e3400582feefe80075d1a`。上述 v3 与失败包 e731 的源 SHA-256 为 `fea6e3ba036badfed4efb2e3fccc00cd8c72bad838af0cb5fadc8fd70800d524`，测试为 `156a8e52ee030b3334c2cd0e6219321ab212ec71a464a8e6bd446a57d8a706cf`。`manifest.json` 中的更早源码指纹及下方四主题截图属于本次窗口边界补充之前的重绘优化阶段，保留作历史证据。
