## 最终实现：独立核验进程与三种时间边界

下文原有长测和录像保留为历史证据。**最终生产源码的本机结果为 `../macos/final-process-smoke.json` 与 `../macos/final-process-delay80.json`**；原目录中早期文件名的“final”不表示它们包含后来加入的进程隔离。当前 Windows 最终生产结果应查上一级报告及 `../windows/`，不能用 macOS 成功替代。**相册外框修复后的最新 1 Hz 复测也发生一次保护暂停，严格连续可见项未通过；此前 1 Hz PASS 仅保留为前一版本的一次历史运行，不能替代最新结果。**

Windows 的诊断确认了两类争用：核验与 Python 界面绘制竞争，以及结果已经完成、Qt 尚未消费的调度等待。最终实现采用一个懒启动的持久核验进程和两块可复用共享帧缓冲区，仍调用原 `compare_candidate_frames`，保留原分辨率、数学流程及全部阈值。Qt 优先消费已完成结果；相册使用模型通知和局部重绘；存在待呈现实时帧且无手势时，业务修改合并到即将发生的画布呈现。

必须区分以下时间，不能把 GUI 排队时间称作算法计算时间：

| 时间 | 最终定义 | 限制或用途 |
|---|---|---|
| 新帧短等待 | 新帧进入待呈现槽到其截止时刻 | 保持 `min(50 ms, 0.85 × 预览周期)`；新帧和重绘不续期 |
| 核验就绪 | 提交到父进程工作线程收到子进程结果 | 含排队、启动、复制、算法与 IPC；用于及时性判断；另记就绪到 Qt 消费的等待 |
| 可呈现帧龄 | 原帧接收到实际发布该帧 | 独立上限为一个预览周期；仍须精确核验同帧、不得倒退序号，不能重复续期 |

此前把短等待的 0.85 周期复用为绝对帧龄和 GUI 消费期限，混淆了上述语义；本次明确拆开。**FPS 相对下降不超过 5%、P95 帧龄相对基线增加不超过一帧的验收条件保持不变**。一次核验尚未及时就绪或源帧过旧时，仍整体隐藏候选并禁止点击；连续 300 ms、至少八次及时核验后恢复，实时预览继续。

每个实际执行过的源代次在其计算之后串行清理，收到子进程重置确认后才释放缓存预算；未执行的重置不创建进程、不积压清理。工作进程异常退出可重建；关闭有界取消 IPC，并确认子进程和共享内存释放。若极端情况下操作系统未能回收自有进程，保留资源所有权和预算并停止提交，不冒称释放成功。安装版 `--self-check --json` 的内部 probe revision 5 会运行真实子进程，校验同图、噪声、漂移、换源、独立 PID 和资源关闭。

## 问题与修复

原实现一旦触发预览回退，每个新帧都会先隐藏候选，核验完成后再显示；有效但稍旧的结果还会反复延长恢复期。只读复现中，同一画面四秒发生 111 次显隐转换。

现实现把已核验帧及其候选原子呈现。完成帧拥有受预算约束的引用，不将旧结果当成新帧的证明；超出预算时统一暂停候选显示及点击，实时画面继续。连续 300 ms、至少八次及时核验后，一次性恢复。恢复恰好由新帧入口触发的竞争条件另有定向测试，禁止恢复后的已核验帧被未核验新帧覆盖。
