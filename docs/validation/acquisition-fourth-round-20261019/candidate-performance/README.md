# 候选对齐与预览呈现性能

2026-10-19，本机 macOS，768×576 合成纹理、实际 Qt Canvas、原分辨率独立候选对齐、每 150 ms 一次自由测量及局部 JPEG95/4:4:4 写入。自动分析使用固定候选替身，**不是全图算法或真实 Microview 延迟测试**。不修改 OpenCV 全局线程配置（本机为 18）。

可重复命令（两种模式分别启动进程，原生运行时保持测试窗可见）：

```sh
QT_QPA_PLATFORM=offscreen .venv/bin/python scripts/validation/benchmark_candidate_preview.py --mode baseline --output /tmp/candidate-baseline.json
QT_QPA_PLATFORM=offscreen .venv/bin/python scripts/validation/benchmark_candidate_preview.py --mode guard --output /tmp/candidate-guard.json
```

macOS 原生将 `offscreen` 改为 `cocoa`，Windows 使用默认平台。Windows 及真实设备必须另行验证。

| Qt 平台 | 基线 FPS | 开启 FPS | 基线 P95 帧龄 | 开启 P95 帧龄 | 开启后候选可点采样比例 | JPEG 保存 |
|---|---:|---:|---:|---:|---:|---:|
| offscreen | 30.283 | 30.450 | 3.732 ms | 14.340 ms | 100% | 50/50 |
| Cocoa | 30.305 | 30.285 | 1.905 ms | 18.943 ms | 100% | 49/49 |

- FPS 按预热后实际绘制的不同帧计算；开启后 offscreen 未下降，Cocoa 下降约 0.067%，均在 5% 限制内。
- P95 帧龄增加分别为 10.608 ms、17.038 ms，小于 33 ms 的一个采集周期。
- Cocoa 基线仅采到 87 个不同可见绘制帧，开启组为 180；基线可能被同机其它原生窗口遮挡。以上原生数值是可见绘制采样，不作为持续无遮挡或真实硬件验收。
- 开启组像素及 scratch 逻辑预算峰值 32,964,608 字节，关闭后为 0；此数不是整个进程 RSS。
- 该固定候选替身的 `analysis_ms` 不反映真实算法速度；只用来验证叠加呈现与写盘并行负载。

## 防闪烁修正的证据

`before-presentation-gate.json` 记录初始直接画新帧的缺陷：31.25 FPS，但候选仅 47.7% 时间可点、394 次绘制中 263 次隐藏。每一帧先显示新图，再等对齐结果，必然产生闪烁。

`after-presentation-gate.json` 记录保持已核验画面、等新帧核验后一起呈现的修正：31.26 FPS、100% 可点、129 次绘制无一次隐藏，P95 帧龄 12.10 ms。对齐等待超过当前采集间隔的 85%（上限 50 ms）则显示最新画面，隐藏并禁用未核验候选；不会停止采集或降低核验阈值。等待槽及工作帧均纳入 FrameBudget，只有一个对齐 worker，没有中间帧队列。

这些 JSON 为实现期局部回归；真实 Microview、拔插、长期动态视场及 Windows 平台的 FPS/帧龄仍需独立验收。

最终门禁进一步限定为精确 `frame_id`，保存最多 8 个已核验帧的标量结果（不保留像素）。较新的合法结果不能认证被跳过的中间偏移帧，旧的已核验显示帧仍可保持标注。补强后 offscreen 复测见 `exact-frame-baseline.json` / `exact-frame-guard.json`：30.291 / 30.301 FPS，P95 帧龄 4.057 / 13.068 ms；开启组 100% 可点、0 次候选隐藏、51/51 张 JPEG 写完，预算回收到 0。这次补测不是 Windows 或真实相机验收。

## 实际自动分析 worker 延迟

`worker-latency.json` 使用用户两张截图中的原 768×576 区域（与计划阶段输入 SHA256 一致），实际运行 spawn、共享内存和 IPC，1 ms 轮询获取结果。每组独立新 worker，先记录首次冷启动，再记录 15 次复用。包括 IPC，不包括相机、稳定等待或 Qt 绘制。

| 截图 | 算法 | 首次冷启动总耗时 | 复用 P50 | 复用 P95 |
|---|---|---:|---:|---:|
| 1 | 传统 | 145.93 ms | 25.32 ms | 25.52 ms |
| 1 | 多尺度 | 261.28 ms | 140.69 ms | 142.65 ms |
| 2 | 传统 | 135.70 ms | 16.65 ms | 17.97 ms |
| 2 | 多尺度 | 226.06 ms | 107.15 ms | 108.60 ms |

工作进程回归 `test_cu_automatic_worker.py`：5 项通过，覆盖真实进程复用、取消后恢复、超时及崩溃重建。macOS 沙箱禁止 `shm_open`，首次沙箱内的 4 项失败属于环境权限；获准在沙箱外运行后全部通过。

## 测试等待器对线程的干扰

完整主窗口最初的视觉脚本用 `QTest.qWait(20)` 循环等待候选，使 Python 对齐线程反复等 GIL，显示出 125 ms 左右的假慢。隔离对照（`wait-driver-probe.json`）仅改变等待方式，同一 BGRA 图和线程：`processEvents()+sleep(2ms)` 为 9～11 ms，`QTest.qWait(20)` 为 795～799 ms，`qWait(5)` 仍为 341～381 ms。正式视觉验证应使用真正 Qt 事件循环或会释放 GIL 的等待器，保持真实帧 ticker 持续运行；不能通过暂停采集绕过门禁。

## 安装版离线诊断字段

`performance_schema` 版本 1 随诊断导出，逐项说明单位和边界。每项最多保留 512 个标量样本，输出 `n / p50 / p95`；无样本输出 `null`，不虚构零延迟。采集统计按最近来源、代际和一次采集运行保留，停止后仍可导出，下次开始清空；分析统计覆盖当前试验工作区运行期。

- `ingest_fps` 是到达控制器且成功接纳的不同实时帧频率，包含上游丢帧影响；`presented_fps` 是完成 Qt 绘制的不同帧频率，同一帧反复绘制标注不重复计数。百分位是帧间隔倒数的分布，`frame_sampling.*.window_fps` 为保留窗口的 `(帧数−1)/时间跨度`。两者都不冒充相机传感器帧率。
- `frame_age_ms` 从 `FrameHandle.received_at` 到首次 Qt 绘制结束；Microview 的起点为原生 SDK 回调内缓冲复制完成时的 QPC 时间，其他来源为适配器摄入时间，和 Python `perf_counter` 使用同一系统性能计数器。它不是曝光到显示的延迟。非法负帧龄不进入百分位，并单独计数。
- `analysis_ms` 包含提交、启动、调度、共享内存、算法、传输及 GUI 轮询；`analysis_to_paint_ms` 还包括首次候选呈现，不能称为单独绘制耗时。
- `analysis_service_total_ms`、`analysis_preparation_ms` 来自工作进程现有服务计时；`analysis_processing_ms` 为两者之差，包含原生调用及结果包装，不修改测径算法。
- `analysis_shared_memory_ms` 是父进程分配与复制；`analysis_budget_wait_ms` 是重计算许可等待；`analysis_process_start_call_ms` 仅记录冷启动的父进程启动调用，不包含完整子进程导入/就绪。
- `analysis_dispatch_to_receive_ms` 是父进程开始发送命令到 reader 完成反序列化；减去服务总耗时后得到 `analysis_startup_transport_overhead_ms`。后者明确合并子进程启动/导入、共享内存附加、IPC/序列化及调度，**不能拆称为独立启动或传输耗时**。这里仅相减各自进程内测得的持续时间，不相减跨进程时钟。
- `stable_wait_ms` 为准备完成且首次独立对齐之后的额外稳定等待；`alignment_ms` 为独立对齐函数时间；`click_to_accept_ms` 从候选 intent 建立到入账，包含排队和核验。

离线 Microview 应在同一设备、同一图像尺寸下分别导出关闭/开启自动分析且均启用相同存档策略的诊断，再比较窗口呈现 FPS 和 P95 帧龄。合成测试记录继续单独保留，不替代真机结论。

加入安装版采样后的 offscreen 连续 JPEG 复测见 `diagnostics-baseline.json` / `diagnostics-guard.json`：独立基准预热后 30.455 / 30.400 FPS（下降 0.18%），P95 帧龄 3.825 / 15.876 ms（增加 12.052 ms，小于 33 ms），开启组 100% 可点、0 次隐藏、52/52 JPEG 写完。诊断自身的整个采集窗口为 30.286 / 30.259 FPS、P95 帧龄 3.382 / 13.661 ms；其窗口包含预热，所以不与预热后基准数值混用。两组关闭后的逻辑预算均为 0。

Windows 首轮诊断测试发现短任务可能缺少可推算的组合开销。实测虚拟机 Python 3.12.13 的 `monotonic` 为 GetTickCount64（15.625 ms 分辨率），而服务计时的 `perf_counter` 为 QPC（约 41.7 ns），见 `../windows/clock-resolution.json`。父进程诊断计时已统一为高分辨率 `perf_counter`，生命周期超时仍沿用 `monotonic`。若服务耗时缺失或相减出现负差，组合开销仍标记 unavailable，聚合为 `n=0 / null`，不钳制成假零值；真实共享内存释放测试也修正了测试变量遮蔽，确保检查实际段名。

## Windows 原生 Qt 性能定位与固定参考缓存

Windows 首轮实际运行未达到门限，因此暂停了候选包构建。以下都是相同 768×576 合成实时帧、33 ms 输入周期、150 ms 一条已接受实测及局部 JPEG 存档；并非 Microview 设备结果。所有原始失败数据保留在 `../windows/`。

| 对照条件 | 关闭 / 开启 FPS | 关闭 / 开启 P95 帧龄 | 说明 |
|---|---:|---:|---|
| 初稿，测试器 1 ms 采样 | 27.743 / 10.029 | 6.269 / 199.018 ms | 未通过；高频 Python 采样放大了线程竞争 |
| 删除测试器采样，生产呈现策略 | 30.164 / 26.084 | 8.343 / 51.904 ms | 仍未通过，不能归因于测试器后直接放行 |
| 同样无采样，即时呈现诊断 | 30.298 / 30.300 | 5.084 / 17.267 ms | 保留精确帧门禁，仅用于分离呈现等待影响，不是交付策略 |
| 固定参考缓存，生产呈现策略 | 30.157 / 29.377 | 5.057 / 31.726 ms | FPS 下降 2.59%，帧龄增加 26.67 ms；本轮局部检查通过 |

缓存仅消除同一批次参考图的重复灰度、标准化、梯度能量和 Hanning 窗准备；当前帧仍逐帧进行原分辨率检查，全部位移、响应、NCC、梯度与纹理阈值不变。`phaseCorrelate` 接收缓存参考的副本，防止反复加窗污染。固定参考缓存与工作区一同持续计入原 64 B/像素的逻辑预算，不在任务间漏计；切换批次后旧任务持有独立缓存，不能恢复旧结果。

该组对齐 P50/P95 从未缓存的 23.23/58.76 ms 降至 16.98/28.58 ms；52/52 张局部 JPEG 写入成功，错误列表为空，关闭后预算归零。控制器灰度/BGR/BGRA 缓存重复等价、低纹理、漂移和预算回归在 Windows 为 32 项通过；本机最后一组含真实自动分析进程、控制器、工作区、画布和预算的回归为 193 项通过。采样脚本现在显式记录 `sample_interval_ms`、`preview_policy` 与 `paint_duration_ms`，最终性能验收应使用 `--sample-ms 0 --preview-policy production`。

标注布局缓存合并后的 30 秒持续压力组（`../windows/performance-*-cache-combined.json`）进一步累计到 199 条同视场记录；20×6 网格在 120 条后复用位置。关闭/开启为 23.687/18.644 FPS，P95 帧龄 7.793/133.612 ms，画布绘制 P95 86.76/96.01 ms，两组 199/199 张证据均成功，**该组尚未达到性能门限**。长测揭示每次新增记录时密集标注重新布局与等待核验之间的放大效应，不能用前述 8 秒局部通过覆盖；原始结果继续保留，当时暂停构建验收并继续修复，最终复测见下一节。上述阶段性结果不替代最终候选包或真实设备验收。

## 最终慢核验回退与长期复测

增量标注布局先将 30 秒组的画布绘制 P95 降到约 14.5 ms，但保留逐帧等待策略时仍只有 22.340 FPS、P95 帧龄 82.571 ms（`../windows/performance-*-incremental-label.json`）。因此增加有界回退：一次呈现等待超预算，或某次独立核验已经落后当前帧时，后续帧直接进入预览，不再每帧重复等待。至少经过 2 秒且连续 8 次及时、精确对应当前帧的核验后，才恢复原有短暂等待策略。恢复期间任一次迟到都会重新开始观察。

回退只控制像素何时呈现。候选绘制、命中、点击提交和最终入账继续要求精确显示帧通过原分辨率对齐检查；旧帧的合法结果不能认证新帧。后台核验保持单任务和最新帧策略，阈值、测值及证据来源均不变。回退次数和恢复状态会导出到 `frame_sampling.candidate_preview`，属于运行诊断，不产生项目修改。

Windows 原生 Qt 最后使用相同 30 秒、同网格及 150 ms 写入负载，执行真实生产代码（`--sample-ms 0 --preview-policy production`）：

|---|---:|---:|
| 预热后不同帧 FPS | 30.3015 | 30.3166 |
| P95 首次绘制帧龄 | 9.155 ms | 18.936 ms |
| 画布绘制 P50 / P95 | 6.622 / 14.565 ms | 5.995 / 11.722 ms |
| 已接受 / 成功存图 | 198 / 198 | 198 / 198 |
| 关闭后的逻辑预算 | 0 | 0 |

见 `../windows/performance-baseline-bounded-preview.json` 与 `../windows/performance-guard-bounded-preview.json`。帧率未下降，P95 帧龄增加 9.781 ms，小于 33 ms，**该模拟持续压力组达到约定性能门限**。开启组的独立核验 P50/P95 为 26.040/35.221 ms，发生 3 次即时预览回退，无测量错误。

候选可用性边界单独保留：开启组 2354 次绘制中，695 次包含可见候选（29.52%）；这是绘制次数比例，**不是墙钟可点击时长、点击成功率或识别准确率**。负载下，新帧先显示、核验完成后候选才恢复，会出现阶段性隐藏和暂不可点。该基准使用固定候选并持续手动接受测量，不冒充持续候选点选验收；真实导航中的候选点击验证与离线 Microview 动态负载仍需分别记录。核验长期慢于实时帧率时，可用点选时间窗口会缩短，不能宣称候选始终可点。

最终本机定向回归原始日志为 `controller-final-pytest.log`：**210 passed in 5.94s**，包括真实自动分析子进程、慢核验连续预览、禁止未核验候选入账、精确当前帧恢复接受、恢复观察期、在途确认、预算与 UI 集成。`controller-final-source.json` 记录 Python/平台、controller/alignment/performance/worker 及相关测试 SHA256。对应 Windows 最后一次定向回归为 154 项通过；完整安装版及真实相机结论由交付总报告单独汇总。
