# 第六轮 macOS 最终回归

产品版本保持 **0.4.10**。本目录结果来自 2026-10-20 冻结源码、隔离配置、768×576 合成相机帧和 Qt offscreen；不是 Microview、Windows 原生窗口或安装版验收。源码指纹保存在各 JSON 中。没有修改视场稳定检测或测径算法。

## 连续预览、JPEG 与相册负载

`performance/` 的基线和候选核验两组依次执行；运行期间停止 Windows VM 测试和构建。每组连续负载 30 秒、随后保持预览和相册 3 秒，33 ms 输入一帧、每 1,000 ms 接受一条实测，局部 JPEG 存档，相册持续打开。每个进程使用独立临时数据。

脚本：`scripts/validation/benchmark_candidate_preview.py`。这是**固定候选样例**下的 Qt 绘制、严格对齐、手工入账、JPEG 和相册性能对照，不运行真实全图算法、不经过主窗口导航；下一节覆盖真实导航和分析。

| 指标 | 基线 | 启用候选核验 |
|---|---:|---:|
| 预览 FPS | 30.3036 | 30.3045 |
| P95 帧龄 | 2.815 ms | 10.748 ms |
| 接受／已写入 JPEG | 30／30 | 29／29 |
| 相册检查 | 通过 | 通过 |
| 关闭后预算占用 | 0 B | 0 B |

FPS 未下降，P95 帧龄增加 **7.933 ms**，小于当前一帧 **32.999 ms** 的预算；通过本机模拟负载的性能门槛。两组是同一冻结代码、同一参数下的基线／核验对照，不是改造前后两个软件版本。

候选首次实际绘制前出现一次准备期暂停和恢复（约 475 ms）；从首次可见绘制开始，连续约 **31.86 秒**没有再次隐藏或暂停。初始准备事件完整保留在 `comparison.json`，未计为“首次出现后闪烁”。不能只用平均帧率推断可见性。

更早一组基线碰到 Windows VM pytest 尾部运行，已明确排除；原始文件保留于 `.tmp/acquisition-sixth-round-20261020/macos-performance-final/baseline-overlap-excluded.json`，没有纳入本表。

复现参数：

```sh
QT_QPA_PLATFORM=offscreen PYTHONPATH=src .venv/bin/python \
  scripts/validation/benchmark_candidate_preview.py \
  --mode baseline --duration 30 --recovery-seconds 3 \
  --frame-ms 33 --measure-ms 1000 --sample-ms 0 --gallery \
  --output <新的基线输出路径>
# 使用相同参数，将 --mode 改为 guard，使用另一个新输出路径。
```

## 真实导航、分析和 100 次画布点选

`clicks100/` 使用 `validate_acquisition_sixth_round.py --scenario clicks --clicks 100`。真实进入采集与试验／含量试验，通过界面设置操作者、类别、标尺和自动开关；运行实际分析工作进程、严格对齐、画布鼠标点击、账本与 JPEG 写入，没有直接注入候选或接受记录。

无录屏运行期间仍暂停 VM 重任务，耗时 21.60 秒：

- **12 批次、100 次点选、100 条入账、100 张 JPEG 保存成功**。
- 接受部分候选后，其余候选 ID 和批次保持；没有剩余候选整组隐藏或呈现暂停。
- 点击到入账 P50／P95：**1.328／3.431 ms**。
- 算法 P50／P95：**63.802／162.832 ms**。
- 分析至首次候选绘制 P50／P95：**84.887／176.338 ms**。
- 操作期间产品源码指纹不变。

这些耗时属于合成图和本机工作进程，不能作为离线 Windows 相机设备的延迟承诺。完整过程和最终画面分别见 `result.json`、`initial.png`、`final.png`。

## 独立录像与未隐藏的失败路径

`clicks12-video/workflow.mp4` 是独立的 **12 次点选／2 个批次**示范，12 条入账和 JPEG 均通过。录像使用 8 fps 的 `QWidget.grab()`，并非系统桌面捕获，录屏结果不纳入上述性能门槛。FFmpeg 解码校验通过。

首次独立录像尝试在第 4 次合成点击等待入账超时，仅接受 3 条；保留于 `video-diagnostics/first-timeout/`。当时没有指针事件诊断，不能断言其唯一原因。

增加验证脚本事件诊断后，一次延长录像在第 2 次点击捕获到明确的安全拒绝路径，保留于 `video-diagnostics/pending-paint-rejection/`：

- 发出合成鼠标按下时，画布已收到第 **46** 帧，但最后实际绘制／公布的呈现令牌仍属于第 **45** 帧。
- 两帧不同，产品拒绝建立手势；未创建手工第一点，也没有发出候选接受事件。
- 此时没有候选显隐变化、歧义菜单、来源变化或新的分析；原批次继续显示。
- 原验证点击门槛只等待“候选可见”，没有等待新帧完成绘制。诊断说明了这个复现的未入账原因，不将其误报为候选闪烁，也不通过放宽产品帧核验来让测试通过。

最终录屏仅修正验证脚本：等待 `presented.frame is canvas.frame` 且候选可见，再发出真实 Qt 点击；不主动公布呈现帧、不修改产品状态或放宽核验。原有保护也可能忽略短暂帧不一致窗口内的实际用户点击，本轮结果不能解读为“每次实际点击必然计入”。按下时的帧不满足要求则应重新点选。

失败 JSON 和截图保留在本目录；失败的完整录像保留于 `.tmp/acquisition-sixth-round-20261020/macos-clicks12-video-final/` 与 `macos-clicks100-video-diagnostic/`。有界输入轨迹、呈现帧、按下／释放前后上下文、拒绝／歧义事件现已加入验证脚本，便于离线复核。无录屏 100 次验收使用原脚本并已通过；最终录像使用修正后的点击等待条件，两者的脚本哈希分别保留在 JSON 中。
