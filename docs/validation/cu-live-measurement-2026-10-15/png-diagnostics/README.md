# PNG 编码诊断归档

本目录保存既有私有探针、原始结果和摘要；整理过程仅用 Python 标准库读取／复制文件，没有重新运行编码、Qt、测试或基准。**这些是方案诊断，不是生产性能验收。最终生产表现以 [R3 性能报告](../R3_PERFORMANCE.md) 的真实工作区数据为准。**

## 身份与采样边界

- 速度原型：[fdm_png_pillow_probe_9b529eb5.py](fdm_png_pillow_probe_9b529eb5.py)，SHA256 `9b529eb5f8743b258e5d51f910be2d38736a19708350fd19c21c8566be717d30`。两平台 smoke 和 6K 速度报告均嵌入此摘要。完整脚本含三种编码路径、写盘提交、解码验证和故障注入；未裁成片段。
- 独立 RSS 原型：[fdm_png_pillow_probe_8aa8f982.py](fdm_png_pillow_probe_8aa8f982.py)，SHA256 `8aa8f98269b4c1262f630a99c344995883ba280f43fb13e667f6f07552e13d8c`。Windows 独立内存总报告嵌入此摘要。macOS 的 12 份独立 RSS JSON 没有内嵌脚本摘要，保留原状；当前脚本的 `--child-memory` 路径与其结构对应，不能把归档关联伪称原 JSON 已记录源码身份。
- 生产模块 `src/fdm/live_experiment/png_stream.py` 的归档时 SHA256 为 `9d48f29b0ede9ca28f7752a4d6e17ae2663586b331c8d54afcb959e79d20470c`，**与两份探针不同**。生产模块增加输入校验、分块压缩输入、取消检查及异常引用释放；本目录原型结果不能直接算作生产模块通过。是否启用、预算接入与最终源码身份另看 R3 生产清单。
- 6K 为 **6144×4096、BGR 72 MiB**，每后端预热 **1 次**、正式计时 **3 次**，四个固定合成场景。脚本默认参数虽为 5／30，实际报告明确为 1／3；本次没有完成计划的 30 次验收。下表仅列本批 P50／P95／最大，3 样本分位数不表示稳定尾延迟。
- smoke 为 512×341、0 次预热／1 次计时；Windows 独立 RSS 总报告中的速度也是 0／1，只作功能／内存诊断，不并入三次速度样本。
- Windows 为现有 Parallels Windows ARM64 虚拟机中的 x64 Python 仿真环境，不能外推真实 Windows x64 用户设备。所有图像均合成；没有真实相机、显微样本、实时画布、GPU 捕获或采集卡负载。

全部原路径、长度、原始 SHA256 与归档 SHA256 见 [manifest.json](manifest.json)。原始 JSON 未补字段、未删失败。

## 选择逐行路径的依据与代价

Pillow 的 BGR `Image.frombuffer(..., "raw", "BGR", ...)` 不是借用原 BGR 数据的零复制路径；原型会创建四字节每像素的 RGB 存储，6144×4096 为 **96 MiB**。独立 RSS 中 Pillow 的增量约 98 MiB，与这份额外图像的量级一致。在原帧还由草稿／预览／证据任务持有的工作区中，不能假设释放一个 Python 局部变量就能释放源帧，因此这份副本不适合紧张的帧预算。

逐行原型只整理当前扫描行，以 SUB 过滤、level=1／Z_RLE 和分块 IDAT 写出，不生成整幅 RGB 副本或完整压缩 PNG 缓冲。独立 RSS 观察到的增量 macOS 约 0.08–0.91 MiB、Windows 约 1.00–1.05 MiB，为采用该结构提供了诊断依据；**这些数值不是生产上界承诺**。生产实现的逻辑 allowance 与 RSS 仍需分别验证。

这里没有选择“所有平台最快”的方案：macOS 四场景里 Pillow 的 P50 均低于逐行原型；Windows 本批逐行原型的 P50 均最低。逐行输出的压缩率也有代价，例如条纹 PNG 322,004 字节，而 OpenCV 为 80,432、Pillow 为 80,196。取舍是有界的编码工作区与可审计的失败路径，同时保留完整无损像素。正式延迟、吞吐、背压和持续预览由 R3 UI 条件决定。
