## 保存崩溃：复现、修复与边界

旧版组合回归 `test_build_support.py + test_build_windows_onedir.py + test_release_self_check.py` 在本轮 Windows 再次触发 `0xC0000005`，退出码 `-1073741819`。旧故障的 WER 记录指向 `shiboken6.abi3.dll + 0x1746a`；本轮 Python 栈仍处于保存结果应用阶段，故障线程没有 Python 帧。保留 [修复前日志](windows-baseline/combined-build.log)、[原故障摘要](windows-baseline/original-crash-summary.txt)。没有取得当时的原生 dump，不把主线程所在的路径解析函数当作故障指令。

确定的生命周期缺陷是：`QThread.finished` 到达 GUI 后，协调器立即丢弃 worker／thread 引用、标记空闲或启动下一次保存，而后台还可能正在处理延迟析构。受控检查让真实 QObject 析构暂停：旧实现此时已经 `busy=false`、两个引用均释放；修复后保持忙碌和引用，GUI 仍处理事件。依据 [Qt 6.10 QThread 文档](https://doc.qt.io/qt-6.10/qthread.html#isFinished)，使用 `wait(0)` 检查线程真正退出，未退出时通过单次定时器继续检查，不阻塞 GUI；确认退出后才释放引用、应用结果、执行排队保存或关闭／切换。

- 新增三种受控回归：保存空闲、接续排队保存、保存后切换。检查后台析构未结束时均不能提前完成，GUI 事件继续分发。
- Windows 保存专项 **28 项通过**。
- 原崩溃组合在修复后连续 **3 轮，每轮 74 项 + 107 子测试通过**。
- 连续 **200 轮、600 次真实后台写入**通过；每轮核对快照隔离、保存期间新修改、重复保存复用和失败回滚，并显式处理延迟删除与 GC。见 [压力数据](windows-fixed/save-stress.json)。
- 不改变项目文件格式、原子写入、失败保留、更新标记或撤销历史；原图保存默认仍关闭。

这些证据支持线程析构交接竞态的修复；不宣称有限次数的压力测试能证明所有环境永不崩溃。

## GUI 发布：程序优化与测量工具干扰分别处理

程序中的实际开销：记录面板折叠或切到其它页时，每根测量仍执行 `scrollToBottom()`，触发不可见表格布局。现在记录与两个表格模型仍同步更新；隐藏表格只标记需要定位，在再次显示并完成布局后滚到最新行。可见列表维持原本即时跟随行为。新增单条、批量、切页、重新展开和换场回归。

另一部分尖峰来自基准工具自己的资源采样线程。300 次展开列表诊断中，全部 7 次超过 4 ms 的发布都与该线程的进程枚举时间重叠，未伴随同等幅度的 GUI 执行周期增加，也没有 GC；该组最大 7.520 ms。对照数据见 `windows-final/sampler-thread.json`。这是测量干扰证据，不据此把所有旧峰值一概归为系统抖动。

基准工具增加独立进程采样，避免与 GUI 共用 Python 解释器，继续采集目标与实际计算子进程的内存，排除采样进程自身；保留线程模式和全部旧数据。诊断的阶段钩子与周期读取也会影响时间，因此下面正式采样关闭插桩。Windows 周期计数只用于诊断，没有转换成毫秒，遵循 [QueryThreadCycleTime 文档](https://learn.microsoft.com/en-us/windows/win32/api/realtimeapiset/nf-realtimeapiset-querythreadcycletime)。
