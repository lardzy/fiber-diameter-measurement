# 采集完成后加载弹窗不退出：复现与修复

日期：2026-09-12。基线：0.4.5 / `a1f3087`。版本号保持不变。

## 结论

本次在 macOS / Qt 6.10.2 上，用用户提供的真实切片的本机副本复现了相同现象：切片文件已经读取、文档已经登记，后台线程已经结束，但“正在加载已采集的数字化切片…”进度窗口随后出现在采集完成提示上方，阻挡正常交互。

原因是进度窗口结束时仅调用 `close()` 和 `deleteLater()`。对于已有 `QWindow`、但尚未创建平台窗口的隐藏进度窗口，`close()` 可以返回成功而不触发 `QProgressDialog.closeEvent()`。其内部的 250 ms 延迟显示定时器仍在运行；紧接着进入完成提示的 `QMessageBox.exec()`，延迟删除还没有执行，旧窗口便被 `forceShow()` 显示出来。

这条进度窗口路径由 2026-09-11 的 `a58931d` 引入，与用户“前天没有问题”的时间线吻合。上一次 `a1f3087` 去除了发布后的多余网络查询，但没有修复本次复现的窗口生命周期问题。

Qt 对尚无平台窗口的关闭操作存在直接返回的路径；进度窗口的 `reset()` 会停止内部显示定时器，而关闭事件会通过取消处理间接调用它。本次直接使用公开接口完成清理，不依赖关闭事件是否被平台派发。[QWindow 6.10.2 源码](https://github.com/qt/qtbase/blob/v6.10.2/src/gui/kernel/qwindow.cpp#L2251)、[QWidget 关闭路径](https://github.com/qt/qtbase/blob/v6.10.2/src/widgets/kernel/qwidget.cpp#L7986)、[QProgressDialog 重置与延迟显示](https://github.com/qt/qtbase/blob/v6.10.2/src/widgets/dialogs/qprogressdialog.cpp#L516)。

## 现场文件与对照证据

对用户提供的共享目录只做只读检查：清水、Herzberg、GraffC 三份切片的清单均为已完成，无遗留的写入侧文件。清水文件约 196.30 MiB，尺寸 15712 × 11764，含 900 张采集图像、9 个焦平面。网络原件没有修改。

只将清水复制到本机，用于真实主窗口、模拟 60 fps 相机消息、真实完成提示以及后续查看的复现。网络发布步骤在此实验中替换为记录调用，不会覆盖共享目录中的成品。

旧加载函数直接取自 `a1f3087`，在相同测试中失败。记录到的顺序为：

1. 清理前进度窗口尚未显示，内部定时器仍活动。
2. `close()` 返回 `True`，但没有收到 `closeEvent()`；定时器仍活动。
3. 在完成提示的事件循环中收到 `showEvent()`，此时 `_io_complete` 已为 `True`。
4. 完成提示和已结束的加载窗口同时可见。

替换清理逻辑后，相同真实数据测试通过。一次本机运行约 44 ms 出现完成提示；提示停留约 0.6 秒，61 次检查均无残留加载窗口。关闭提示后，查看切片、切换到原生视场并等待精确图像可用通过。这是本机复现证据，不是 Windows 安装包或网络吞吐性能验收。

## 修改

- I/O 成功、失败、取消后的共同清理路径明确调用 `reset()` 停止内部显示定时器，再调用 `hide()` 移除窗口，最后延迟删除。工作线程退出前仍不允许关闭窗口来脱离事务。
- 后台工作结束后发送排队信号退出等待循环，20 ms 定时器只负责进度显示。取消仍等待实际文件操作退出，不遗留读写线程，也不将正常完成误记为取消。
- 进度更新只修改窗口拥有的 `QProgressBar`，避免模态 `QProgressDialog.setValue()` 隐式处理事件而重入界面回调。Qt 官方文档明确提示这一行为。[进度值与事件重入](https://doc.qt.io/qt-6/qprogressdialog.html#value-prop)。
- 增加文件读取、文档安装的阶段诊断。界面仅更新内存记录；独立观察线程写入已有的本机 `startup.log`，不依赖控制台或 GUI 定时器。观察线程最多 4 个，阶段记录最多 16 条，慢操作在 5/30/120 秒各记录一次 Python 线程栈；不修改用户操作，不新增弹窗。

完成通知依赖进度定时器是另一处已验证的脆弱点：测试故意禁止进度定时器触发，旧实现无法结束已完成的操作，新实现正常返回。Windows 消息循环可能推迟低优先级计时器消息；这项加固不能被当作本次现场发生计时器饥饿的证据。[Microsoft WM_TIMER](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-timer)。

阶段诊断在 Windows 无控制台包中同样使用本机日志路径。Python 观察线程不能保证捕获一直持有 GIL 的原生死锁，也不提供强制打断 SMB 系统调用的能力。

## 回归

新增测试保留真实 `QMessageBox.exec()`，从外层事件循环触发采集完成，保持完成提示超过 250 ms，并在提示打开期间检查加载窗口可见性和当前模态窗口。覆盖正常完成后关闭、中断保留后查看，以及后台准备、发布、文档挂载的连续进度窗口。两项新增集成测试在修复前均失败，修复后通过。原先完成提示被替换为空操作的测试无法覆盖这个时间窗口。

另覆盖：没有控制台且进度定时器不可用时，连续成功和失败均正常退出；正常结束不触发取消；可见进度更新不重入 GUI 回调；取消等待 worker 退出；日志阻塞不无限增加观察线程；连续采集不启动隐藏渲染器；发布失败保留本机恢复文件；发布成功后不重新查询共享目录。

相关 10 个测试文件按数字切片、网络采集、响应式 I/O、阶段诊断和日志筛选，在同一进程中 **219 项通过，249 项未选中，耗时 21.69 秒**。另有真实切片本机副本测试 1 项通过，编译检查和 `git diff --check` 通过。

扩展回归的第一次运行停在旧的滚轮导航测试关闭 SQLite 的操作上，原生采样同时显示还有后台线程在打开数据库。该测试单独运行通过，但缺少画布清理；现已在关闭源文件前调用 `canvas.shutdown()` 并释放画布，与主窗口的资源清理顺序一致，随后完成上述整组运行。没有将被中止的运行算作通过，也没有据此认定现场存在同一 SQLite 问题。

仍须用重新构建的 Windows 安装包，在真实相机和局域网环境复测连续采集、完成后关闭和查看。
