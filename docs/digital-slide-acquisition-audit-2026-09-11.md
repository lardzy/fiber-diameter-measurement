## 结论

发现了可以独立复现的电机恢复缺陷、逐帧界面重复布局、无上限的预览帧投递，以及局域网文件操作阻塞界面线程等问题。**这些问题值得修复，但目前还不能把 Windows 上“连续采集后，10 分钟任务变为 30 分钟”归结为已经实机确认的单一原因。**

用户补充：长时间停留的是“未设置输出路径”的警告框；控制失效时相机仍正常，关闭整个软件后电机恢复。因此分别验证普通警告框、实时帧处理和电机状态恢复，不能用系统文件选择窗口的行为直接解释该场景。

## 1. 电机恢复：状态源不一致

代码位置：[进入采集与自动启用电机](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/ui/main_window.py:15276)、[统一会话清理](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/ui/main_window.py:28000)、[电机 shutdown](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/services/motion_control.py:151)。

`_prepare_transition()`、设备丢失处理会执行 `MotionController.shutdown()`：控制器设为 `enabled=False`，串口关闭。但是 UI 的“启用电机输出”没有同步取消勾选。

随后进入数字切片模式时，自动启用逻辑只调用复选框 `setChecked(True)`。复选框本来就是 True，不会再次发出 `toggled` 信号，实际的 `set_enabled(True)` 因而没有执行。相机已重新启动，与电机的失效状态相互独立。

使用假的串口句柄、真实主窗口逻辑验证：

| 操作 | 相机活动 | UI 勾选 | 电机 enabled | X / Z 命令被接受 |
| --- | --- | --- | --- | --- |
| 初次进入 | 是 | 是 | 是 | 是 / 是 |
| 连续 10 次测量工作区→采集工作区 | 是 | 是 | 是 | 是 / 是 |
| 执行设备切换的统一清理后重新进入 | 是 | 是 | **否** | **否 / 否** |
| 手动取消勾选，再勾选 | 是 | 是 | 是 | 是 / 是 |
| 设备丢失处理后重新进入 | 是 | 是 | **否** | **否 / 否** |

**边界：仅切换“测量分析”和“数字切片”的 10 次循环没有复现。** 上述缺陷覆盖设备切换、设备丢失和使用统一资源清理的退出路径；用户具体触发了哪条路径，还需要 Windows 日志对应，不能声称所有退出重进都会发生。

另有两个控制路径风险：重新进入时总是自动选择优先串口，可能覆盖用户手选的另一个端口；串口写入同步发生在 UI 线程，只设置了读取超时，没有设置 `write_timeout`。后者在 Windows 驱动异常时存在长时间等待的条件，但未用真实硬件复现。

建议让控制器状态作为唯一事实来源：关闭、失败、端口切换均同步 UI；重新进入时显式执行启用操作并检查结果，不能依赖复选框是否发信号。保留仍有效的用户选定端口，只有原端口缺失时才重新推荐。串口错误应结束当前控制动作并呈现实际状态；重连不应自动补发旧移动命令。

## 2. 每一张预览帧都触发工具栏结构变更

代码位置：[实时预览帧安装](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/ui/main_window.py:15084)、[预览分析控件刷新](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/ui/main_window.py:26801)、[工作区状态同步](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/ui/main_window.py:13771)、[工具栏上下文布局](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/ui/widgets.py:1433)。

每帧执行 `_update_action_states()`，继而更新工具图标、按钮、预览上下文和工作区。数字切片模式下尤其存在来回设置：先按“预览活动”显示普通预览上下文，随后又按“数字切片工作区”将它隐藏。工具栏自身即使隐藏，也会重新移除并插入布局项、激活父布局。

这与之前修复的 `AdaptiveLayoutController` 强制切换侧栏是不同入口。旧侧栏问题的幂等保护仍有效；当前重复开销发生在 `MeasurementToolStrip` 及逐帧状态刷新。

本机 1600×1200 预览、1920×1080 窗口的诊断对照：

| 仅用于定位的实验 | 单帧 UI 安装 P50 | P95 |
| --- | ---: | ---: |
| 原始路径 | 4.66 ms | 5.05 ms |
| 临时跳过工具栏布局安放 | 2.23 ms | 2.52 ms |
| 临时跳过整套按钮状态刷新 | 1.37 ms | 1.59 ms |
| 恢复原始路径 | 4.81 ms | 5.09 ms |

120 帧 profile：总计 0.666 秒，其中 `_update_action_states` 累计 0.488 秒；出现 720 次布局 `insertWidget` 调用和 49,920 次主窗口事件过滤调用。**对照只用于定位，跳过控件更新不是最终实现，也不是已交付的优化成绩。**

此外，每帧复制原始图像、生成显示缩图；相机后端无法直接提供尺寸时，状态卡为读取尺寸又复制整帧。每帧还重复 `fit_to_view()`。这些都应按实际变化触发或使用已有帧元信息。

建议帧回调只更新图像与必要的帧状态；工作区、设备、工具栏按状态变化更新。正确计算数字切片模式的上下文可见性，再让布局操作幂等，避免只在单个 setter 上加判断而仍产生“显示→隐藏”的循环。图像适配只在尺寸、窗口或显示策略改变时执行。

## 3. 预览队列没有上限，采集的新帧判断依赖 UI 到达顺序

代码位置：[预览信号投递](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/services/capture.py:460)、[等待停稳后新帧](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/ui/main_window.py:17271)、[接受采集帧](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/ui/main_window.py:17294)。

`_deliverFrame` 逐张通过 QueuedConnection 投递 `QImage`，没有合并、队列容量或旧帧淘汰。会话 generation 可以拒绝其他会话的帧，但旧图像仍须等到事件被消费才释放，不能控制队列占用。

构造 UI 暂时不消费的场景后，120 张不同的 1600×1200 RGB32 帧均仍存活，像素数据约 878.9 MiB。恢复时全部 120 帧按顺序进入 UI，一次 `processEvents()` 耗时约 580 ms。内存数值是由仍存活 QImage 的实际尺寸计算，**不是进程 RSS，也不是警告框测试测得的积压**。

更关键的是 `_preview_frame_serial` 在 UI 安装时才递增，采集用它判断停稳以后有没有新帧。构造测试：先产生并投递红色帧，尚未处理其信号；然后进入等待新视场阶段；再处理之前排队的帧。分别设置丢弃 0 帧和 3 帧，预先排入 1 帧和 4 帧，两种情况都在没有产生后续新帧时接受了旧帧。这里只使用替身接收结果，没有写入真实采集数据。未发现用户已有切片错误，不能据此断言已有文件受影响。

建议将帧拆为两条逻辑用途：

- **显示**使用只保留最新帧的有界邮箱，同一时刻最多一个待处理唤醒，停止会话立即释放旧帧引用。
- **采集**使用在采集线程接收处生成的会话 ID、源帧序号及时间戳。停稳后建立源端水位，保持丢弃帧规则，不将显示帧率或 UI 投递次数当作采集时序。

已经接受的采集图像、请求式分析帧及落盘任务不能套用“只保留最新”的淘汰规则。不能通过简单丢弃 UI 回调或降低采集分辨率解决问题。

## 4. 局域网操作仍可能冻结界面

代码位置：[完成与发布](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/ui/main_window.py:17609)、[发布文件实现](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/services/digital_slide_cache.py:392)、[渲染器来源指纹](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/services/digital_slide_renderer.py:131)。

当前已经支持 UNC 和 Windows 映射网络盘识别，网络采集先写本机暂存，完成后再发布。因此不能说每张图块都直接写 SMB。

但剩余同步路径包括：

- 开始前对目标路径执行存在性、目录创建、磁盘空间检查。
- 完成时在主线程复制文件并 `flush/fsync`、替换最终文件。虽然进度回调会处理 Qt 事件，但一次底层写入或刷盘未返回时，回调无法帮助界面恢复。
- 创建切片浏览画布时，渲染器构造函数仍对原网络文件执行 `is_file/stat` 计算缓存指纹，哪怕实际像素读取路径已经是本机副本。

为避免把本机盘速度当成网络结论，只对模拟原始路径的两次状态查询各注入 300 ms 延迟，像素数据仍读用户切片的本机只读路径：两次查询均记录在 `MainThread`，浏览器创建约 867 ms，16 ms 心跳最大间隔约 878 ms。此实验确认阻塞位置，**不代表真实网络延迟就是 300 ms**。

这些调用主要解释开始、完成、挂载或重新显示切片时的停顿；不能单独解释整个后续采集过程持续三倍耗时。

建议把目标检查和网络发布放到受会话管理的后台 I/O 任务，保留现有暂存、原子替换、失败恢复文件语义。源文件版本信息由后台准备后交给渲染器，不能在 UI 构造时再次请求网络文件状态。发布过程中要显示明确状态，退出、重复开始、失败重试都要遵循同一个任务生命周期。

## 6. 额外发现：大尺寸采集帧可能永久等待写入队列

代码位置：[写入队列接纳规则](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/ui/main_window.py:776)、[UI 重试](/Users/lishuyang/PycharmProjects/fiber-diameter-measurement/src/fdm/ui/main_window.py:17438)。

队列默认字节预算为 64 MiB。5000×4000 RGB32 单帧约 76.3 MiB，空队列也永远拒绝；连续 3 次调用均返回 False，队列仍为 0。上层把它当成暂时忙碌，每 50 ms 重试，无法自行取得进展。

默认采集宽度 1600 通常不会触发。选择原始尺寸或大输出分辨率时才有这一条件，**不是已确认的本次现场原因**。应区分暂时排队和不可接纳的单帧；在明确的内存约束下支持一张合法大帧，或者开始前给出清晰错误，不能进入无限重试。

## 建议修复顺序与验收

1. **恢复控制的状态一致性**：覆盖进入退出、切相机、关闭项目、设备异常、串口失效；UI 必须反映控制器实际状态。相机恢复不能被视作电机已经恢复。
2. **先处理帧时序和显示积压，再减掉重复 UI 工作**：采集时间戳/源序号独立于显示；预览有界；工具栏布局和适配操作只在需要时执行。设置变更、采集接受和分析请求继续可靠送达。
3. **移走同步网络操作并延迟初始化浏览器**：未选择查看时只保留文档；后台发布支持状态追踪、失败恢复及退出等待。延迟查询不得覆盖新会话或新输出路径。
4. **补齐队列与串口边界**：超大帧、磁盘满、写入失败、连接关闭与重新启用均能退出等待状态。

Windows 包应增加低频汇总的运行时诊断：相机后端/分辨率、源帧与显示帧数、最大帧年龄及保留字节、UI 心跳 P95/最大间隔、定时器计划与实际触发差值、编码与写入耗时、发布耗时、活跃渲染/写入任务数，以及电机端口、启用状态、启停原因和最近写入结果。记录本机文件，避免每帧同步日志本身增加负担。

现场验收应使用同一 Windows 包、相机配置、真实局域网目标连续完成多个任务；覆盖警告框长时间停留、完成提示不查看、进入退出、切换设备及重新控制 X/Y/Z。将采集期间、结束发布、打开浏览分别计时，再判断“10 分钟→30 分钟”主要发生在哪个阶段。当前本机测试不能替代这一结论。

参考 Qt 对话框 API：[QMessageBox 官方文档](https://doc.qt.io/qt-6/qmessagebox.html)。对话框具有平台实现差异，普通警告框的本机结果不能直接推导 Windows 包的表现。
